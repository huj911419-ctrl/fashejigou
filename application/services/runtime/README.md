# 接实物之前：运行记录与控制准备

这一批代码围绕三个实际问题：电机为什么停了、控制任务有没有长时间没运行、后续角度保持怎样计算。
前两项已经接入现有云台/摩擦轮固件。角度控制核心已实现独立计算，尚未接入电机输出。
原有遥控器使能、停机、故障锁定和恢复条件继续决定运行权限。

## 1. 查询此前发生了什么

USB 输入 `events`，得到最近 **32 条** 状态首次观测或变化；查询不会清除记录。若前一份 USB 报告尚未发送完，会回复 BUSY。
电脑可以先发 `stream off`，等当前输出结束，再发 `events`。

每条记录包含序号、开机毫秒、事件名称、首次/变化标志、旧值和新值。下面只是格式示例，不是实机数据：

```text
[event] seq=21 t_ms=2500 key=rc.online kind=CHANGE previous=0x1 value=0x0
[event] seq=22 t_ms=2500 key=yaw.enable kind=CHANGE previous=0x1 value=0x0
```

这表示软件先记录到遥控离线，再记录到云台撤销使能。它有助于排查，但顺序是各任务实际写入记录的顺序，不证明硬件故障的因果先后。
`INITIAL` 表示第一次看到这个字段，不能把其 previous=0 当作曾经无故障或曾经关闭。

| 字段 | 数值含义 |
| --- | --- |
| `yaw.port`、`rc.online`、`yaw.enable`、`dm.on` | 0/1，分别对应端口就绪、有效遥控在线、应用使能、电机反馈 ON |
| `yaw.stage` | 0 BOOT、1 DISCOVER、2 STOPPING、3 SET_MODE、4 CHECK_MODE、5 READY、6 STARTING、7 RUNNING、8 FAULT |
| `yaw.fault` | 位 1 配置、2 发送、4 超时、8 电机、16 命令 |
| `yaw.inhibit` | 最近控制决定的禁止运行原因，可组合；位 1 配置、2 命令、4 执行器、8 时序、16 速度请求、32 开关关闭、64 需要重新解锁、128 启动请求非零；0 不代表电机 ON |
| `yaw.io_history` | 累计位 1 UART、2 CAN、4 接收溢出；再次发生相同位不生成新变化，次数另看 IO 统计 |
| `friction.fault` | 位 1 配置、2 命令、4 离线、8 温度、16 周期、32 驱动 |
| `friction.enable_mask`、`friction.online_mask` | 位 1/2/4 对应 F1/F2/F3 |
| `friction.phase` | 0 停止、1 升速、2 到位、3 掉速恢复、4 故障、5 单轮/部分轮测试 |
| `imu.stage` | 0 BOOT、1 RESET_WAIT、2 PROBE、3 CONFIG_WRITE、4 VERIFY、5 READY、6 FAULT |
| `imu.fault` | 位 1 SPI、2 芯片 ID、4 配置读回、8 无新数据、16 范围、32 设备状态 |
| `attitude.stage` | 0 校准、1 跟踪、2 丢失、3 配置错误 |
| `attitude.fault` | 位 1 数据、2 时序、4 数据源、8 配置 |
| `attitude.control_valid` | 0/1；仍要求安装轴确认、有效且连续的航向 |

相同状态重复一万次也只保留首次记录；发生变化才追加。容量满后覆盖最旧记录，并报告 `overwritten`。
时间戳和序号会按 uint32 回绕，按输出的先后顺序读，不要跨回绕按序号数值排序。
历史只在 RAM 中，复位/断电后丢失，不是 Flash 黑匣子，也不保存每个控制周期的波形。
未连接电脑时仍可记录；电脑端 `tools/usb_console.py` 已支持 `events`。

`yaw.inhibit` 解释最近一轮实际执行的分支，不是原始开关状态，也不是电机故障码。
例如启动非零原因可能只持续一轮，随后变为“需要重新解锁”；可结合历史看最初原因。
逐位说明和处理顺序见 [云台为什么没有运行](../diagnostics/README.md#云台为什么没有运行)。

## 2. 看任务有没有来不及运行

USB `status` 新增 `yaw_timing`、`imu_timing` 或 `friction_timing`：

| 项目 | 含义 |
| --- | --- |
| `calls` | 记录过多少轮调用；第一次只建立时间基准 |
| `interval_ms` | 最近两轮调用时间间隔 |
| `max_interval_ms` | 记录以来最大的调用间隔 |
| `over_limit` | 间隔超过允许上限的次数 |
| `same_ms` | 两次调用落在同一毫秒的次数 |

上限直接取现有配置：云台控制 10 ms、IMU 10 ms、摩擦轮 5 ms。正常计划周期分别是 2/2/1 ms，二者含义不同。
第一次调用不会把全部开机时间记成一次超期。计数到 UINT32_MAX 后饱和，不从最大值跳回零。
这些数据统计的是**调用间隔**，精度为 1 ms，不是函数执行耗时、CPU 占用率、RTOS 栈余量，也不代替实机实时性测量。
统计本身不修改使能条件；控制器原来的周期和失联保护仍独立执行。

## 3. 云台角度控制准备到哪一步

新增 [`module/control/yaw_angle`](../../../module/control/yaw_angle/README.md)：输入连续目标角度和实际角度，输出角速度。
支持 PI、速度/加速度限制、限制期间的条件积分、命令/反馈时效检查、坐标零点变更检查和故障锁定。
它不读取硬件、不发送 CAN、不创建任务。云台构建清单会编译它以检查 ARM 兼容性；目前无人调用它，链接器会移除未使用代码。

后续组合还需要：确认 IMU 安装轴和电机正方向、建立角度零点/连续角规则、确认传动关系、决定切换角度模式时如何捕获目标，再做实机参数整定。
当前 `gimbal_bench` 仍然运行遥控速度模式。

## 4. 文件组织与移植

```text
module/system/loop_stats       调用间隔统计，纯 C、调用者持有实例
module/system/event_history    状态变化环形记录，纯 C、调用者持有实例
application/services/runtime    事件名称和共享记录的同步适配
application/services/diagnostics USB 查询和显示
module/control/yaw_angle        独立角度外环，纯 C、调用者持有实例
```

控制/IMU 任务在发布状态时记录变化，不增加一个后台任务，也不在中断里打印。
通用记录器没有 HAL/RTOS 依赖；换平台时，实现已有 `control_platform` 的时钟和短临界区即可。
记录/快照临界区只进行有界数据访问。32 条快照约 640 字节，诊断使用静态快照存储，避免占用大块任务栈；上板后仍需检查临界区时间。
两个 bench 各有一份 RAM 历史，仍与旧哨兵应用独立。

## 5. 后续提前开发的顺序

1. 实物参数明确后，把角度核心接到云台模式管理，保留手动速度模式用于调试。
2. 整机组合时统一分配 CAN/UART 和控制权，再接遥控、调试、视觉命令来源；目前两个台架不能直接拼接同名 HAL 回调。
3. 扩展参数导出、版本校验和保存策略；当前在线调参只改 RAM，Flash 保存应根据存储布局确定。
4. 确定 Pitch 和供弹机构后，再实现对应驱动、机械限位和协调逻辑。

现阶段可以离线验证算法、协议、超时、恢复、数值边界与记录顺序。电机方向、安装轴、机械限位、合适 PID、温漂及供弹负载必须由实物确认。
